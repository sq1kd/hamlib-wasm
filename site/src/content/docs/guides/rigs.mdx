Hamlib reports several hundred serial models, and every one of them is in the
catalogue (`hamlib.models`). Being in the catalogue only says the backend goes
through Hamlib's common serial port layer, so each `RigModel` also says how far
it is supported:

| Field | Meaning |
| --- | --- |
| `support` | `"verified"` when a browser test in this package drives the model through an emulated serial port; otherwise `"candidate"` |
| `limitation` | Set when this build cannot drive the model, with the reason |
| `serialRateMin`, `serialRateMax` | The baud range the backend declares |
| `serialDataBits`, `serialStopBits`, `serialParity`, `serialHandshake` | The line settings the backend declares |

`VERIFIED_MODELS` lists the verified models with the tests that cover them, and
`UNUSABLE_MODELS` the models that cannot work in this build and why.

:::note[Tested on real radios]
Two radios on our desk run the opt-in hardware suite
(`mise run test-hardware`): the **QRP Labs QMX+** and the **Yaesu FT-710**.
It opens each one through the shipped Node transport and the real Wasm build,
reads frequency, mode and PTT, and can round-trip a frequency write. What we
found on them is under [Notes from real radios](#notes-from-real-radios).
:::

:::caution
`support: "verified"` is narrower than "works": it means a browser test in this
repository drives the model through an emulated serial port, in Chromium and
Firefox, on every change - the Kenwood TS-480, the Icom IC-703 over CI-V and the
Yaesu FT-710 over newcat. Every other model is a candidate: worth trying, not
promised.
:::

## Line settings

Both transports accept the same line settings: 7 or 8 data bits, 1 or 2 stop
bits, none/even/odd parity, and no flow control or RTS/CTS hardware flow
control (XON/XOFF is not supported). A model that declares anything else fails
with `-RIG_ECONF` before the port is opened, so a user never ends up on a
silently downgraded port. Its `limitation` field
says so up front, and the [live demo](../../demo/) shows it when you pick the
model.

## Baud rate

No field can carry the rate the radio itself is set to: a backend declares a
range, and the radio's menu picks the value inside it. A "verified" model can
still be opened at the wrong rate, which produces silence rather than an error.
`open()` therefore checks that the rig answered and rejects with the rate it
tried; `detectBaudRate()` searches the declared range. See
[Baud rate](../rig-api/#baud-rate).

## Other limitations

- **Serial only.** Network (`rigctld`, TCP) and USB-HID rigs are not reachable
  over a serial transport.
- **One call at a time per module.** The module is single-threaded; calls
  serialize on one queue. Several rigs can share a module, but their calls
  take turns.
- **No cancellation of a stuck call.** A call that overruns `callTimeoutMs`
  leaves the module unusable (`RIG_HUNG`); dispose it and create a new one.
- **Browser support.** Web Serial exists only in desktop Chromium-based
  browsers and Firefox 151+, in a secure context; see
  [Where it runs](../../getting-started/#where-it-runs).

## Notes from real radios

What we, and the people who send
<a href={repositoryPage('/issues/new?template=rig-report.yml')}>rig reports</a>,
found on real radios, one section per radio in the same shape: how it was
connected, what works, what is Hamlib's own behaviour, and how to work around
it. Hamlib issues are noted as they are, not patched here.

### QRP Labs QMX+

**Tested** 2026-11-17, Node, USB (CDC, `0483:a34c`), Hamlib model `QMX`, 9600 baud.

**Works:** frequency, mode and PTT, read and write; keying PTT; an unplugged
cable fails the next call with `HAMLIB_ERROR`, and the rig reopens after it is
plugged back in.

**Hamlib's model data:**

- Transmit is declared as 4-14 MHz, CW and data modes only, 5-100 W.
  `powerToMilliwatts()` fails outside that and reports 100 W for full power.
- The radio's DIGI mode reads as `PKTLSB`.
- No Morse: `sendMorse()` is `UNSUPPORTED_OPERATION`. The radio itself keys
  text sent with the Kenwood `KY` command, in CW mode:

  ```ts
  await rig.raw.sendRaw(new TextEncoder().encode('KY CQ TEST;'));
  ```

- No S-meter is advertised.

### Yaesu FT-710

**Tested** 2026-11-17, Node, USB (CP2105 dual UART, `10c4:ea70`; CAT is the
first of its two ports), 38400 baud.

**Works:** frequency, mode and PTT; the `STRENGTH`, `RFPOWER`,
`RFPOWER_METER` and `SWR` levels; PTT keys the transmitter and `getPtt()`
reports keyer transmission as `on` too; full break-in (`FBKIN`), which the
radio only accepts in a CW mode.

**Hamlib's backend:** `sendMorse()` stores the text in the radio's CW TEXT
memory 1, overwriting it, then sends `KY6;`, which the FT-710 does not accept,
so nothing is transmitted. Play the memory yourself:

```ts
await rig.sendMorse('CQ TEST');                               // stores TEXT memory 1
await rig.raw.sendRaw(new TextEncoder().encode('KY01;'));     // plays it
```

The radio plays it only with its keyer on, and transmits it only with
break-in on; otherwise it beeps. `KY00;` stops the playback.
