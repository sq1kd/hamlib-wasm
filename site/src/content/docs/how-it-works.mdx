## Why not write it from scratch?

Every radio speaks its own CAT dialect. A Kenwood takes plain text like
`FA00007074000;`. An Icom wraps binary frames in `FE FE … FD`, and on its
shared CI-V bus it hears its own command echoed back, which has to be read and
thrown away before the answer. Yaesu's older radios take five-byte binary
commands, its newer ones a text protocol of their own. And then the
individual quirks: the FT-920 wants 80 ms of quiet after every command, and
the PCR receivers are sent the power-on command twice because the first one
sometimes gets "off" as its answer.

[Hamlib](https://hamlib.github.io/) has been collecting that knowledge since
2000. Its volunteers wrote the backends, and programs like WSJT-X, fldigi and
`rigctl` use them every day, so the quirks were found on real radios and fixed
upstream. This build alone carries {models.length} models.

A new JavaScript CAT library would have to find every one of them again. We
would rather not. So we take Hamlib as it is, compile it to
WebAssembly, and give it a way to reach a serial port from a web page or a
Node process. The backends are Hamlib's code, unchanged, so a model behaves
here the way `rigctl` drives it. When Hamlib fixes a backend, we move the pin
and the fix arrives here too.

What we add is the plumbing Hamlib never needed on a desktop: a serial port
that lives behind a promise, a TypeScript API, and the build that ties them
together.

untouched.

Three tricks let us do this without patching Hamlib's logic:

**The C code blocks; the browser can't.** Hamlib calls `write()` and waits for
the answer, the way C on a desktop does. Web Serial and `serialport` answer with
promises. Emscripten's [Asyncify](https://emscripten.org/docs/porting/asyncify.html)
pauses the whole C call stack while the promise settles, then resumes it as if
`write()` had simply returned.

**Hamlib's I/O is redirected at link time.** Rather than edit Hamlib's port
layer, we have the linker swap its `read()`, `write()`, `select()` and `nanosleep()`
for small wrappers (`-Wl,--wrap=…`). The file descriptor Hamlib holds is a
handle into the JavaScript transport, so upstream's read loop, timeouts and
retries stay in charge of the protocol.

**Everything is single-threaded, so everything queues.** Asyncify can only
pause one call at a time. Every call, from every rig, goes through one queue
per module, in order. Calls never overlap, though a sequence of them is not
atomic; the [Raw API guide](../guides/raw-api/#one-queue) explains what that
means for you.

Apart from putting our `serial.c` in place of upstream's, the only change to
Hamlib's source is
{REPOSITORY_URL === null ? 'one small patch' : <a href={`${REPOSITORY_URL}/blob/main/${patch}`}>one small patch</a>}: it skips the Morse
keyer thread, which a single-threaded build can't start, and leaves out the
network and dummy models that could never open over a serial port.

## How the package is built

One config file goes in, one npm package comes out.

<BuildSteps />

The generator is the step worth knowing about. It reads clang's AST of Hamlib's
headers and binds a function only if `rigctl` itself calls it and every type
maps cleanly to TypeScript. Anything else is refused, with the reason written
to `coverage.json`, rather than bound as a guess. That is where the `RawRig`
methods come from, and why each one matches a Hamlib call by name.
